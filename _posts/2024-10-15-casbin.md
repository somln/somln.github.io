## Casbin 도입 이유

사용자의 권한 관리를 하다보면 단순하게 "admin / user"로 나누는 것만으로는 부족한 경우가 있다. 특정 사용자에게만 예외적으로 권한을 주거나, 특정 리소스에 대한 접근을 세밀하게 제어해야 하는 상황들이 생겼길 수 있기 때문이다.

그래서 접근 제어 라이브러리인 Casbin을 찾게 되었고, 직접 적용하면서 개념부터 구조, 사용법까지 정리해봤다.

---

## Casbin이란?

Casbin은 오픈 소스 기반의 권한 제어 라이브러리다. 권한 제어의 핵심 개념은 다음 세 가지다.

- **주체(subject)** — 누가
- **객체(object)** — 무엇에
- **행동(action)** — 어떤 작업을 하려는가

Casbin은 이 세 가지 요소를 기준으로 접근을 허용할지 거부할지 판단한다. 단순한 ACL(Access Control List)뿐 아니라, RBAC(Role-Based Access Control), ABAC(Attribute-Based Access Control) 등 다양한 모델을 지원한다는 게 특징이다.

예를 들어 회사 조직처럼 계층 구조를 가진 권한 관리가 필요하거나, 사용자 속성(나이, 지역, 등급 등)에 따라 접근을 다르게 해야 하는 복잡한 시나리오에도 대응할 수 있다.

## 주요 특징

Casbin이 다른 권한 관리 라이브러리와 차별화되는 점은 다음과 같다.

**다양한 권한 모델 지원**
- RBAC, ABAC, ACL 등 상황에 맞는 접근 제어 모델을 선택할 수 있다.
- 하나의 모델에 고정되지 않고, 프로젝트 요구사항에 따라 유연하게 변경 가능하다.

**멀티 언어 지원**
- Java, Go, Node.js, Python 등 주요 언어에서 동일한 인터페이스로 사용할 수 있다.
- 언어가 바뀌어도 정책과 모델 정의는 그대로 유지할 수 있어서 재사용성이 높다.

**다양한 저장소 연동**
- 파일, DB, 메모리, Redis 등 다양한 저장소를 Adapter만 교체해서 쉽게 변경할 수 있다.
- 개발 환경에서는 파일로, 운영 환경에서는 DB로 관리하는 식의 전환이 간편하다.

**유연한 확장성**
- 모델과 정책 문법을 직접 정의하거나, 기존 정책에 추가 규칙을 덧붙일 수 있다.
- 커스텀 함수를 작성해서 복잡한 비즈니스 로직도 권한 검사에 포함시킬 수 있다.

한 가지 주의할 점은, Casbin은 **인증**을 직접 다루지 않는다는 것이다. "누가 로그인했는가"는 별도의 인증 시스템(JWT, OAuth 등)에서 처리하고, Casbin은 그 이후의 **권한** 판단만 담당한다.

## 기본 사용 흐름

Casbin을 사용할 때 핵심이 되는 객체는 **Enforcer**다. Enforcer는 "주어진 요청이 정책에 부합하는가"를 판단하는 역할을 한다. 전체적인 흐름은 다음과 같다.

### 1. 모델 정의 (model.conf)

먼저 `model.conf` 파일에 접근 제어의 구조를 정의한다. 아래는 가장 기본적인 형태의 ACL 모델이다.

```ini
[request_definition]
r = sub, obj, act # 요청 구조 정의: 주체, 객체, 행동

[policy_definition]
p = sub, obj, act # 정책 구조 정의: 정책이 다룰 요소들

[policy_effect]
e = some(where (p.eft == allow)) # 하나라도 allow면 허용

[matchers]
m = r.sub == p.sub && r.obj == p.obj && r.act == p.act # 일치 조건
```

간단히 말하면, "요청(r)이 정책(p)과 완전히 일치하면 허용한다"는 의미다.

각 섹션을 조금 더 자세히 보면:
- **request_definition**: 권한 검사할 때 전달되는 요청의 형태를 정의한다.
- **policy_definition**: 정책 파일에 저장될 정책의 구조를 정의한다.
- **policy_effect**: 여러 정책이 매칭될 때 어떻게 처리할지 정의한다. (하나라도 allow면 허용, 모두 allow여야 허용 등)
- **matchers**: 요청과 정책을 어떻게 비교할지 로직을 정의한다.

### 2. 정책 정의 (policy.csv)

이제 실제 사용자 권한을 정책 파일로 정의한다.

```csv
p, alice, data1, read
p, bob, data2, write
```

이 정책의 의미는:
- alice는 data1을 read(읽기)할 수 있다.
- bob은 data2를 write(쓰기)할 수 있다.

### 3. Enforcer 생성

Java를 기준으로 Enforcer를 생성하는 코드는 다음과 같다.

```java
Enforcer e = new Enforcer("path/to/model.conf", "path/to/policy.csv");
```

모델 파일과 정책 파일의 경로를 넘겨주면 Enforcer 객체가 생성된다. 이 객체가 권한 검사의 핵심 역할을 담당한다.

### 4. 권한 검사

이제 `enforce()` 메서드로 권한을 검사할 수 있다.

```java
String sub = "alice";
String obj = "data1";
String act = "read";

if (e.enforce(sub, obj, act)) {
    // 허용됨
    System.out.println("접근 허용");
} else {
    // 거부됨
    System.out.println("접근 거부");
}
```

Casbin은 내부적으로 matchers 조건에 따라 정책을 비교하고, 그 결과에 따라 true/false를 반환한다. 위 예시에서 alice가 data1을 read하려는 요청은 정책과 일치하므로 true가 반환된다.

## Model 문법 정리

Casbin의 `model.conf`는 기본적으로 다음 4가지 섹션으로 구성된다.

| 섹션 | 역할 | 필수 여부 |
|------|------|----------|
| request_definition | 권한 검사 시 전달되는 요청 인자 정의 | 필수 |
| policy_definition | 정책의 구조 정의 | 필수 |
| policy_effect | 여러 정책이 일치할 경우의 처리 방식 정의 | 필수 |
| matchers | 요청과 정책을 비교하는 로직 정의 | 필수 |

추가로 RBAC 같은 역할 기반 모델을 사용할 때는 `role_definition` 섹션도 필요하다.

예시를 하나 더 보자:

```ini
[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[policy_effect]
e = !some(where (p.eft == deny)) # deny가 없으면 허용

[matchers]
m = r.sub == p.sub && r.obj == p.obj && r.act == p.act
```

여기서 `policy_effect`를 보면 "deny가 하나도 없으면 허용"이라는 의미다. 이런 식으로 정책 효과를 다양하게 정의할 수 있다.

## RBAC: 역할 기반 접근 제어

Casbin의 가장 대표적인 강점 중 하나가 바로 RBAC 모델이다. RBAC에서는 "사용자 → 역할 → 리소스"의 관계로 권한을 관리한다. 즉, 사용자에게 직접 권한을 부여하는 게 아니라, 역할에 권한을 부여하고 사용자에게 역할을 할당하는 방식이다.

### 기본 RBAC 예시

**model.conf**

```ini
[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, p.sub) && r.obj == p.obj && r.act == p.act
```

**policy.csv**

```csv
p, admin, data1, read
p, admin, data1, write
g, alice, admin
```

위 설정의 의미는:
- admin 역할은 data1에 대한 read와 write 권한을 가진다.
- alice는 admin 역할을 상속받는다. (`g, alice, admin`)
- 따라서 alice는 admin이 가진 모든 권한을 갖게 된다.

여기서 `role_definition`의 `g = _, _`는 "첫 번째 인자가 두 번째 인자의 역할을 상속받는다"는 의미다. 그리고 matcher에서 `g(r.sub, p.sub)`를 사용해서 역할 상속 관계를 확인한다.

## 계층형 RBAC (Hierarchical RBAC)

Casbin은 역할 간의 상속도 지원한다. 예를 들어, manager 역할이 editor 권한을 포함하도록 정의할 수 있다.

```csv
g, alice, manager
g, manager, editor
p, editor, data1, write
```

이 경우 alice는 다음과 같은 권한 상속 경로를 갖는다:
- alice → manager → editor
- 따라서 alice는 editor가 가진 data1에 대한 write 권한을 갖게 된다.

이런 계층 구조는 조직도처럼 복잡한 권한 체계를 표현할 때 매우 유용하다. 예를 들어 "팀장은 팀원의 모든 권한을 가진다" 같은 규칙을 간단하게 구현할 수 있다.

## 도메인 기반 RBAC

다중 테넌트 환경이나 조직별로 권한을 분리해야 하는 경우, 도메인 개념을 추가할 수 있다.

```ini
[role_definition]
g = _, _, _ # 세 번째 인자가 도메인
```

```csv
p, admin, group1, data1, read
g, alice, admin, group1
```

이렇게 설정하면:
- alice는 group1 도메인 내에서만 admin 권한을 가진다.
- group2 같은 다른 도메인에서는 alice의 admin 권한이 적용되지 않는다.

멀티테넌트 SaaS 서비스를 만들 때 특히 유용한 기능이다. 같은 사용자가 회사A에서는 admin이지만 회사B에서는 일반 사용자일 수 있는 상황을 깔끔하게 표현할 수 있다.

## ABAC: 속성 기반 접근 제어

ABAC은 사용자나 리소스의 "속성"을 기준으로 권한을 판별하는 방식이다. 예를 들어, 나이가 18세 이상인 사용자만 특정 컨텐츠에 접근할 수 있게 하거나, 파일 소유자만 삭제할 수 있게 하는 등의 세밀한 제어가 가능하다.

```ini
[matchers]
m = r.sub.age >= 18 && r.obj == p.obj && r.act == p.act
```

```csv
p, /adult_content, read, allow
```

이렇게 하면 요청자의 age 속성이 18 이상일 때만 /adult_content에 접근할 수 있다.

더 복잡한 예시로, 평가식을 정책에 포함시킬 수도 있다:

```ini
[matchers]
m = eval(p.sub_rule) && r.obj == p.obj && r.act == p.act
```

```csv
p, r.sub.age >= 18 && r.sub.premium == true, /vip_content, read, allow
```

이런 방식으로 복잡한 비즈니스 로직을 권한 검사에 포함시킬 수 있다. "18세 이상이면서 프리미엄 회원만 VIP 컨텐츠에 접근 가능"같은 규칙을 코드 수정 없이 정책만으로 표현할 수 있다는 게 큰 장점이다.

## EnforceContext — 다중 정책 관리

때로는 하나의 시스템에서 여러 종류의 정책을 동시에 사용해야 할 수 있다. 예를 들어 RBAC와 ABAC 정책을 함께 사용하거나, 일반 권한과 관리자 권한을 별도로 관리하고 싶을 때 EnforceContext를 활용할 수 있다.

```java
EnforceContext ctx = new EnforceContext("2");
e.enforce(ctx, user, resource, action);
```

ctx의 suffix 값(예: "2")에 따라 Casbin은 p2, r2, m2 등의 섹션을 자동으로 참조한다. 즉, 같은 모델 파일 안에서 r/p/m/e 세트를 여러 버전으로 구분해서 사용할 수 있다.

예를 들어 model.conf에 다음과 같이 정의할 수 있다:

```ini
[request_definition]
r = sub, obj, act
r2 = sub, obj, act, domain

[policy_definition]
p = sub, obj, act
p2 = sub, obj, act, domain

[matchers]
m = r.sub == p.sub && r.obj == p.obj && r.act == p.act
m2 = r2.sub == p2.sub && r2.obj == p2.obj && r2.act == p2.act && r2.domain == p2.domain
```

이렇게 하면 일반 권한 검사는 기본 enforcer로, 도메인 기반 권한 검사는 context를 사용해서 따로 처리할 수 있다.


## 마무리하며
Casbin은 정책과 모델을 분리해서 권한 로직을 명확하게 관리할 수 있는 구조를 가지고 있다.

프로젝트가 커질수록 권한 관련 로직이 복잡해지고 코드 곳곳에 섞이기 쉬운데, Casbin을 쓰면 이걸 외부 정책으로 분리해서 관리 부담을 줄일 수 있다. 정책이 바뀔 때 코드 수정이나 재배포 없이 정책 파일이나 DB만 수정하면 된다는 점도 실용적이다.

또한 RBAC으로 역할을 정의하고, ABAC으로 속성 기반 제어를 보완하며, EnforceContext로 여러 정책을 조합할 수 있는 구조라서 다양한 권한 요구사항에 유연하게 대응하기 좋다.

다음 포스트에서는 SpringBoot에서 역할 기반 권한에 사용자별 예외 처리를 결합한 도메인 RBAC를 적용한 과정을 다뤄보려 한다.
