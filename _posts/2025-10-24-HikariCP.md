## 분석 배경
운영체제를 공부하면서 뮤텍스, 세마포어, 스레드 동기화 등의 개념을 배웠지만, 실제 프로덕션 코드에서 이런 개념들이 어떻게 적용되는지 궁금했다. 취준생 입장에서 토이 프로젝트를 진행하다 보면 대규모 트래픽이나 동시성 문제를 직접 겪을 기회가 많지 않기 때문에, 배운 개념들이 어떻게 쓰이는지 감이 잘 오지 않았다.

그래서 실제 프로덕션 환경에서 검증된 오픈소스를 분석하면 이런 궁금증을 해결할 수 있겠다고 생각했고, HikariCP가 그 목적에 잘 맞을 것 같아 선택했다. HikariCP는 JDBC 커넥션 풀 라이브러리로, Spring Boot 2.0부터 기본 커넥션 풀로 채택될 정도로 성능과 안정성이 검증되었다. 공식 벤치마크에서 다른 커넥션 풀(Apache DBCP, C3P0, Tomcat Pool) 대비 훨씬 빠른 성능을 보였는데, 이는 동시성 제어와 성능 최적화에 상당히 집중한 설계 덕분이다.

HikariCP의 코드를 분석하면 운영체제에서 배운 동시성 개념들이 실제로 어떻게 구현되는지, 그리고 왜 이런 최적화가 필요한지 구체적으로 이해할 수 있을 것 같았다. 이번 글에서는 `HikariDataSource` 클래스를 중심으로, 멀티스레드 환경에서 어떤 문제를 어떻게 해결하고 있는지 분석해보았다.

## HikariDataSource 아키텍처

`HikariDataSource`는 애플리케이션이 HikariCP를 사용하는 진입점이다. 표준 JDBC `DataSource` 인터페이스를 구현하며, 실제 커넥션 관리는 내부의 `HikariPool`에게 위임한다.

### 클래스 구조

```java
public class HikariDataSource extends HikariConfig 
                              implements DataSource, Closeable {
    
    private final AtomicBoolean isShutdown = new AtomicBoolean();
    private final HikariPool fastPathPool;
    private volatile HikariPool pool;
    
    // ...
}
```
- `isShutdown`: 종료 상태를 원자적으로 관리
- `fastPathPool`: 즉시 초기화된 풀 
- `pool`: 지연 초기화용 풀 

## 1. 초기화 전략

### 두 가지 초기화 방식

HikariDataSource는 두 가지 방식으로 초기화될 수 있다.

#### 방식 1: 기본 생성자 (Lazy Initialization)

```java
public HikariDataSource() {
    fastPathPool = null;
}
```

```java
// 사용 예
HikariDataSource ds = new HikariDataSource();
ds.setJdbcUrl("jdbc:mysql://localhost:3306/mydb");
ds.setUsername("user");
ds.setPassword("password");
```

이 방식에서는 객체 생성 시점에 풀을 만들지 않는다. 첫 `getConnection()` 호출 시점에 풀이 생성된다.

#### 방식 2: HikariConfig 생성자 (Eager Initialization)

```java
public HikariDataSource(HikariConfig configuration) {
    configuration.validate();
    configuration.copyStateTo(this);
    
    LOGGER.info("{} - Starting...", configuration.getPoolName());
    pool = fastPathPool = new HikariPool(this);
    LOGGER.info("{} - Start completed.", configuration.getPoolName());
    
    this.seal();
}
```

```java
// 사용 예
HikariConfig config = new HikariConfig();
config.setJdbcUrl("jdbc:mysql://localhost:3306/mydb");
config.setUsername("user");
config.setPassword("password");
HikariDataSource ds = new HikariDataSource(config);
```

이 방식에서는 객체 생성과 동시에 풀이 초기화된다. 이때 `fastPathPool`에도 풀 참조를 저장한다.

### final과 volatile: 초기화 방식에 따른 필드 선언

`pool`을 volatile로 선언한 이유는 지연 초기화 특성 때문이다. 지연 초기화 방식에서는 이미 여러 스레드가 실행 중인 상태에서 풀을 생성하게 되므로, 멀티코어 환경에서 각 CPU 코어 간의 캐시 동기화가 필요하다. volatile 키워드는 쓰기 시 모든 CPU 코어에 즉시 반영되고 읽기 시 항상 최신 값을 읽도록 보장하여 메모리 가시성 문제를 해결한다.

반면 `fastPathPool`을 final로 선언한 이유는 즉시 초기화 방식의 특성 때문이다. 즉시 초기화는 생성자에서 풀을 생성하므로 단일 스레드 환경이며, 멀티스레드 동기화를 고려할 필요가 없다. final 필드는 생성자 완료 후 모든 스레드에서 안전하게 읽을 수 있도록 Java가 보장하므로, volatile보다 빠르면서도 안전하다.
```java
@Override
public Connection getConnection() throws SQLException {
    if (isClosed()) {
        throw new SQLException("HikariDataSource has been closed.");
    }
    
    // FastPath: 즉시 초기화된 경우
    if (fastPathPool != null) {
        return fastPathPool.getConnection();
    }
    
    // SlowPath: 지연 초기화 경로
    HikariPool result = pool;
    if (result == null) {
        synchronized (this) {
            result = pool;
            if (result == null) {
                validate();
                pool = result = new HikariPool(this);
                this.seal();
            }
        }
    }
    
    return result.getConnection();
}
```

위 코드에서 즉시 초기화된 경우 `fastPathPool`이 null이 아니므로 바로 반환한다. 이때 final 필드는 CPU 캐시를 활용할 수 있어 읽기 비용이 매우 낮다. 지연 초기화된 경우 `fastPathPool`이 null이므로 `pool`을 확인하게 되는데, volatile로 선언되었기 때문에 매번 메인 메모리에서 최신 값을 읽어야 하므로 final보다 읽기 비용이 높다.

## 2. Double-Checked Locking

SlowPath의 초기화 로직을 자세히 살펴보면 `result == null`를 2번 체크하고 있는데, 이것이 **Double-Checked Locking** 패턴이다.
```java
HikariPool result = pool;
if (result == null) {  // 첫 번째 체크
    synchronized (this) {
        result = pool;
        if (result == null) {  // 두 번째 체크
            validate();
            pool = result = new HikariPool(this);
            this.seal();
        }
    }
}
```

### 두 번 체크하는 이유

멀티스레드 환경을 시뮬레이션해보자.
```
시간 T0: pool = null

시간 T1:
    Thread A: if (pool == null) → true, synchronized 진입 대기
    Thread B: if (pool == null) → true, synchronized 진입 대기
    Thread C: if (pool == null) → true, synchronized 진입 대기

시간 T2:
    Thread A: synchronized 획득, pool = new HikariPool() 실행
    Thread B: synchronized 대기 중
    Thread C: synchronized 대기 중

시간 T3:
    Thread A: synchronized 해제
    Thread B: synchronized 획득
    Thread C: synchronized 대기 중

시간 T4 (두 번째 체크가 없다면):
    Thread B: pool = new HikariPool() 또 실행! ← 문제!
    
시간 T4 (두 번째 체크가 있다면):
    Thread B: if (pool == null) → false, 풀 생성 안 함 ← 안전!
```

두 번째 체크가 없다면 synchronized에 진입한 모든 스레드가 풀을 생성하려고 시도한다. 이는 다음과 같은 문제를 일으킨다.
- 불필요한 풀 객체 여러 개 생성 (리소스 낭비)
- 버려진 풀의 커넥션들이 정리되지 않음 (메모리 누수)
- 여러 풀 인스턴스 존재로 인한 상태 불일치

### synchronized = 임계 구역
```java
synchronized (this) {
    // 임계 구역: 한 번에 하나의 스레드만 실행 가능
    if (result == null) {
        pool = result = new HikariPool(this);
    }
}
```

Java의 `synchronized`는 운영체제의 **뮤텍스(Mutex)** 와 유사하게 동작한다. 한 번에 하나의 스레드만 이 블록에 진입할 수 있다.

### 로컬 변수 사용의 이유
```java
HikariPool result = pool;  // 로컬 변수에 복사
if (result == null) {
    // ...
}
return result.getConnection();
```

`pool`은 volatile이므로 매번 읽을 때마다 메인 메모리에 접근하는 비용이 발생한다. 로컬 변수에 한 번 복사하면 이후에는 CPU 캐시를 활용하여 빠르게 접근할 수 있다.

따라서, 지연 초기화 코드에서 확인할 수 있는 최적화는 다음과 같다. 첫째, 로컬 변수 복사를 통해 volatile 필드를 여러 번 읽어야 하는 상황에서 메인 메모리 접근 횟수를 최소화하여 읽기 성능을 향상시킨다. 둘째, Double-Checked Locking 패턴을 통해 이미 풀이 생성된 이후에는 synchronized 블록 진입을 완전히 우회하여 락 오버헤드를 제거하고, 풀이 생성되지 않은 초기 상황에서는 여러 스레드가 동시에 진입하더라도 단 하나의 풀만 생성되도록 보장한다. 결과적으로 지연 초기화 방식에서도 안전성과 성능을 모두 확보할 수 있다.

## 3. 원자적 종료 보장
`isShutdown`은 DataSource가 종료 되었는지를 저장하는 변수이다. 여기서는 Boolean이 아닌 AtomicBoolean이 사용된다.

```java
private final AtomicBoolean isShutdown = new AtomicBoolean();

@Override
public void close() {
    if (isShutdown.getAndSet(true)) {
        return;
    }
    
    var p = pool;
    if (p != null) {
        try {
            LOGGER.info("{} - Shutdown initiated...", getPoolName());
            p.shutdown();
            LOGGER.info("{} - Shutdown completed.", getPoolName());
        } catch (InterruptedException e) {
            LOGGER.warn("{} - Interrupted during closing", getPoolName(), e);
            Thread.currentThread().interrupt();
        }
    }
}
```

### 왜 AtomicBoolean을 사용하는가?

일반 멀티 스레드 환경에서 다음과 같은 문제가 발생할 수 있다.

#### Race Condition 시나리오

```
시간 T0: isShutdown = false

시간 T1:
    Thread A: if (isShutdown) → false 읽음
    Thread B: if (isShutdown) → false 읽음 (A가 아직 true로 안 바꿈!)

시간 T2:
    Thread A: isShutdown = true 쓰기
    Thread B: isShutdown = true 쓰기

시간 T3:
    Thread A: pool.shutdown() 호출
    Thread B: pool.shutdown() 호출 ← 중복 호출! 에러 발생!
```
Thread B가 isShutdown을 읽은 시점에서는 값이 false였지만 그 사이 Thread A가 isShutdown = true를 쓰면 Thread B는 pool.shutdown()를 중복 호출하게 되는 것이고 에러가 발생한다. 하지만 AtomicBoolean를 사용하면 이를 방지할 수 있다.

### AtomicBoolean의 동작 원리

```java
if (isShutdown.getAndSet(true)) {
    return;
}
```

`getAndSet(true)`는 **원자적 연산**이다. 다음을 하나의 분할 불가능한 연산으로 수행한다.

```
1. 현재 값을 읽는다
2. 새 값(true)으로 설정한다
3. 이전 값을 반환한다
```

이는 CPU 레벨에서 하나의 명령어로 처리되므로 중간에 다른 스레드가 끼어들 수 없다. 또한, 락을 거는 것이 아니기 때문에 synchronized보다 훨씬 빠르다는 장점이 있다.

#### 멀티스레드 시나리오

```
시간 T0: isShutdown = false

시간 T1:
    Thread A: getAndSet(true) 실행
              → 현재 값 false 읽고, true로 변경, false 반환
              
    Thread B: getAndSet(true) 대기 (CPU 레벨에서 대기)

시간 T2:
    Thread A: false를 반환받음 → 계속 진행
    Thread A: pool.shutdown() 실행

시간 T3:
    Thread B: getAndSet(true) 실행
              → 현재 값 true 읽고, true로 변경, true 반환
    
    Thread B: true를 반환받음 → 즉시 return!
```
`getAndSet(true)`는 원자적 연산이므로 "값 읽기 → 변경 → 반환" 과정에 다른 스레드가 끼어들 수 없다. Thread A가 getAndSet(true)를 실행하는 순간 isShutdown이 true로 변경되므로, 이후 Thread B가 getAndSet(true)를 실행하면 이미 true인 값을 읽게 된다. 따라서 Thread B는 즉시 return하여 shutdown()을 중복 호출하지 않는다. 이를 통해 단 한 번의 종료만 보장된다.

##  4. 설정 봉인 

```java
public HikariDataSource(HikariConfig configuration) {
    configuration.validate();
    configuration.copyStateTo(this);
    
    pool = fastPathPool = new HikariPool(this);
    
    this.seal();  // 설정 잠금
}
```

### seal()의 역할

`seal()` 메서드는 설정을 읽기 전용으로 만든다.
```java
public void seal() {
    this.sealed = true;
}

public void setMaximumPoolSize(int maxPoolSize) {
    if (sealed) {
        throw new IllegalStateException("Configuration is sealed");
    }
    this.maxPoolSize = maxPoolSize;
}
```

풀 초기화 이후에는 모든 설정 변경 시도가 예외를 발생시킨다.

### 왜 설정을 잠그는가?

풀 실행 중 설정이 변경되면 심각한 문제가 발생한다.
```
시간 T0: maximumPoolSize = 10, 현재 커넥션 8개

시간 T1:
  Thread A: getConnection() 호출
            - maximumPoolSize 읽기 → 10
          
  Thread B: setMaximumPoolSize(5) 호출
            - maximumPoolSize를 5로 변경
          
시간 T2:
  Thread A: 새 커넥션 생성
            
결과: 최대 5개인데 9개 존재!
```

이는 전형적인 Race Condition으로, 설정을 읽는 시점과 사용하는 시점 사이에 값이 변경되어 일관성이 깨진다.

### 불변성과 스레드 안전성

설정을 불변으로 만들면 동기화가 불필요하다.
```java
// 가변: synchronized 필요
class MutableConfig {
    private int maxPoolSize;
    
    public synchronized int getMaxPoolSize() {
        return maxPoolSize;
    }
}

// 불변: synchronized 불필요
class ImmutableConfig {
    private final int maxPoolSize;
    
    public int getMaxPoolSize() {  // 락 없음!
        return maxPoolSize;
    }
}
```

불변 객체는 값이 변하지 않으므로 여러 스레드가 동시에 읽어도 안전하며, Race Condition이 원천적으로 차단된다. 또한 Java는 final 필드에 대해 생성자 완료 후 모든 스레드가 올바른 값을 볼 수 있도록 보장한다. 결과적으로 seal()은 멀티스레드 환경에서 안전성과 성능을 동시에 확보하는 동시성 제어 기법이다.

## 이런 최적화가 필요한 이유

**HikariDataSource는 싱글톤이지만 수천 개의 스레드가 동시에 접근할 수 있다.**

### 실제 프로덕션 환경

```java
@Configuration
public class DataSourceConfig {
    @Bean
    public DataSource dataSource() {
        // 이 객체는 애플리케이션에서 단 하나
        HikariDataSource ds = new HikariDataSource();
        ds.setJdbcUrl("jdbc:mysql://localhost:3306/mydb");
        ds.setMaximumPoolSize(20);
        return ds;
    }
}

@RestController
public class UserController {
    @Autowired
    private DataSource dataSource;  // 모든 컨트롤러가 같은 인스턴스
    
    @GetMapping("/users")
    public List<User> getUsers() {
        // 수천 명의 사용자가 동시에 호출 가능
        Connection conn = dataSource.getConnection();
        // ...
    }
}
```
dataSource.getConnection()가 호출되면 위에서 분석했던 HikariDataSource 클래스의 getConnection()메서드가 호출되는 것이다.

## 결론
Spring Boot를 사용한 일반적인 애플리케이션 개발에서는 이런 수준의 최적화를 직접 구현할 일이 거의 없다. Spring이 싱글톤을 보장해주고, 대부분의 로직은 상태를 메모리에 저장하기보다는 DB나 외부 저장소를 통해 관리하며, 개인 프로젝트에서는 극한의 성능 최적화가 필수적이지 않기 때문이다.

하지만 HikariCP 같은 라이브러리의 코드를 분석하면서, 대규모 트래픽을 처리하는 인프라 레벨의 코드는 확실히 다르다는 것을 알게 되었다. 초당 수만 건의 요청을 처리해야 하는 환경에서는 작은 최적화 하나하나가 비용을 결정한다는 것을 느꼈다.

막연하게 운영체제 이론을 외우는 것보다, 실제 프로덕션 코드에서 어떤 상황에 어떤 동시성 개념이 사용되는지 구체적으로 보니 훨씬 이해가 잘 되었다. 뮤텍스, 메모리 가시성, 원자적 연산 같은 개념들이 어떤 문제를 해결하기 위해 존재하는지, 그리고 왜 이런 최적화가 필요한지를 실제 코드를 통해 배울 수 있었다. 앞으로 멀티스레드 환경에서 코드를 작성할 때 이런 관점을 가지고 접근하면 더 나은 선택을 할 수 있을 것 같다.
